# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Private Homebrew tap for the 21Stark fleet (`21StarkCom/homebrew-tap`, referenced by brew as `21StarkCom/tap`). Each entry installs a **code-signed macOS arm64** build pulled from a **private** GitHub Release asset — signing is either ad-hoc (hermod, frigg, plume, stark-statusline: the linker's signature) or Developer-ID **+ notarized** (idun, alfred, bragi, heimdall, lumiere, tyr, sleipnir's Swift `mac-helper`, brain's native modules, and the mimir, atlas and goldfinger apps); lucius ships no Mach-O of its own beyond the Anthropic-signed `claude` its SDK vendors. **CLIs are formulae in `Formula/`; GUI `.app`s (Mímir, Atlas, Goldfinger) are casks in `Casks/`** (`brew install --cask 21StarkCom/tap/{mimir,atlas,goldfinger}`) — a `.app` belongs in a cask, not a formula. The mimir cask's zip is the notarized + **stapled** `Mimir.app` with the nested `mimir` CLI symlinked onto PATH by a `binary` stanza; the goldfinger cask's is the stapled `Goldfinger.app`, whose one executable (daemon and CLI) its `binary` stanza symlinks onto PATH; the atlas cask ships `Atlas.app` with **no `binary` stanza** (its bundled CLI closure must not shadow the `brain` formula). Formulae come in four shapes: Go single binaries (alfred, frigg, heimdall, lumiere, plume, stark-statusline, tyr; bragi ships a Swift helper beside its Go one), `bun build --compile` single binaries (idun, hermod), Bun source trees run under the keg `bun` (lucius, sleipnir), and **`brain`, a node-ESM `pnpm deploy` tree** installed into `libexec` and run under the keg `node` (see "Adding a formula").

## Big picture

Two facts drive everything here:

1. **Native authenticated downloads.** Each entry puts `Accept: application/octet-stream` and a stripped token from Homebrew's own lookup (`GitHub::API.credentials`: `HOMEBREW_GITHUB_API_TOKEN`, else `gh auth token` from Homebrew's own gh, the only one it looks for, else a keychain token) on its GitHub API asset URL: `headers:` for formulae. Casks retain a small initialization-only adapter that sets the same native download metadata, because cask URL headers are serialized verbatim by `brew info --json`. Homebrew owns preflight, redirects, cache freshness, and partial resume. Never override `_fetch` or issue curl commands in the tap. When that lookup finds nothing, the entry raises `CurlDownloadStrategyError.new(url, guidance)`: during formula evaluation or cask downloader initialization. Formula metadata commands therefore require a token too. Homebrew's sandboxed `build.rb`, `test.rb` and `postinstall.rb` workers reload the formula with gh's config (`~/.config/gh`) and the login keychain unreadable, so gh cannot answer there; they never download, so formulae skip both the lookup and the raise in them, matching a worker by its full path under `HOMEBREW_LIBRARY_PATH` (the path `Sandbox.ruby_command` launches it by). A formula cannot hand them the token through `ENV` either: Homebrew restores `ENV` after evaluating a formula. Homebrew redacts only `ENV` secrets from its output, so with a gh-only login, `--verbose --debug` and `HOMEBREW_CURL_VERBOSE` print the gh token in the curl command line.

2. **This tap is a passive publish target — it does not build anything.** Three lines per formula/cask are release-specific and change every release: `version`, the numeric **asset id** inside the `url`, and `sha256`. Do **not** hand-edit them. Each source repo's release step calls the bumper (below), which reads the asset id and sha256 back from the published release, rewrites those lines and opens a PR here; `README.md`'s caller table names the release step that calls it for each entry. Bump *commits* land as `chore: bump <entry> to <tag> (asset <id>)`; the matching *PR title* is the same subject without the `(asset <id>)` suffix, `--ticket STARK-<n>` scopes both to `chore(STARK-<n>): …`, and the squash subject is drafted from that PR title. The bumper edits those three fields with anchored per-field regexes, not by line position, so reordering `url`/`version`/`sha256` in a formula (e.g. a RuboCop `ComponentsOrder` fix) never breaks a future auto-bump.

**Keep release fields compatible with the bumper.** Preserve standalone `url "…",`, `version "…"`, and `sha256 "…"` stanzas, each exactly once; the bumper refuses an entry with more or fewer. Auth headers are continuation arguments to the URL. Never move the asset pin into a helper or interpolate the version into it.

Platform: `depends_on :macos` + `depends_on arch: :arm64`. Apple Silicon only; a tool that also runs on Linux builds there from source in its own repo (sleipnir, stark-statusline, mimir and goldfinger have no Linux build, and tyr no longer ships a CLI).

## Commands

```sh
# Install (consumer) — token needs read access to 21StarkCom private repos
brew install gh && gh auth login    # or: export HOMEBREW_GITHUB_API_TOKEN=<github PAT>
brew install 21StarkCom/tap/idun

# Lint / audit a formula edit (run from repo root)
brew style Formula/idun.rb
brew audit --strict 21StarkCom/tap/idun       # add --online to check the URL/homepage

# Same for the cask (a GUI app). A cask's asset-id URL fails the unversioned-URL
# audit by design, and atlas also needs `,token_conflicts` (homebrew/core's atlas)
brew style Casks/mimir.rb
brew fetch --cask 21StarkCom/tap/mimir        # checks the registered clone's pinned sha256
brew audit --cask --strict --except=sha256_no_check_if_unversioned 21StarkCom/tap/mimir

# Exercise the real install + the formula's `test do` block (needs the token)
brew reinstall 21StarkCom/tap/idun
brew test 21StarkCom/tap/idun

# Preview a bump (any checkout), and run the bumper's tests (local only: a bare
# remote and a stubbed gh; BUMP_TEST_BASH=/bin/bash runs bump.sh under bash 3.2)
scripts/bump.sh <entry> <tag> --dry-run
scripts/test-bump.sh
```

The tap is already registered locally, but the registration is a **separate git clone** at `/opt/homebrew/Library/Taps/21starkcom/homebrew-tap`, not a symlink to this checkout. `brew style Formula/idun.rb` accepts an explicit path and checks this working tree. Modern `brew audit` rejects path arguments; `brew audit --strict 21StarkCom/tap/<name>` reads the registered clone instead, and so does `brew fetch --cask 21StarkCom/tap/<name>`. `brew fetch --cask` takes a cask path only under `HOMEBREW_DEVELOPER=1`, which is how to check an edited cask's download against its `sha256`. Check syntax and style before merging, then verify that clone is clean, fast-forward it to the merged formula, and run the named audit. Confirm the registered formula matches the reviewed version, asset ID, and checksum before trusting the result. Never discard another process's changes in that shared clone. `brew test` runs only the `test do` block, so keep those assertions **version-agnostic**: assert `version.to_s` against the tool's `version` output rather than a hardcoded string (see `STARK-908`, commit `590f38a`).

**The bumper is `scripts/bump.sh`, and its `--help` is the reference** (21stark ADR-0008). A release clones this tap's `main` and runs the script from that clone; to re-point an entry by hand, run it from a clean checkout of this repo at `origin/main` (`--dry-run` previews, `--no-pr` edits the checkout without committing). Callers run `main` unpinned, so the interface only grows, and a bumper change lands with its tests (`scripts/test-bump.sh`) in the same PR.

Use `idun gh pr-open` and `idun gh pr-merge` for the PR gates. A PR under a ticket carries it in its title (`chore(STARK-<n>): bump <entry> to <tag>`, `docs(STARK-<n>): …`); the bumper's `--ticket STARK-<n>` produces that title, so pass it wherever a ticket exists. A change below the operator rules' ticket bar (a config tweak, a doc fix, a dependency bump) opens with `idun gh pr-open --no-ticket` under an unscoped title, and the unattended CI mergers' bump PRs (idun, alfred, plume) stay unscoped too. A bump PR that a ticket covers but that opened under an unscoped title needs a retitle and its `no-ticket` label dropped, in one command (`gh pr edit <n> --title … --remove-label no-ticket`): `idun gh pr-merge` reads the live title, and skips its ticket stamp while the label stays. Every PR run of `scripts/bump.sh` keeps the label in step with the PR's title: a title naming no ticket carries it, and `--ticket` retitles and then drops it (`scripts/bump.sh --help`). Bumpers open their PRs with plain `gh pr create`, so `idun gh pr-open`'s checks never run on them: review the entry diff, asset id and checksum yourself before merging. Run native Codex xhigh review, fix findings, and rebase before squash-merging. The scanner may flag a formula's public 64-hex checksum as high-entropy; verify it against the downloaded release bytes before using `--allow-secret-commit` on `idun gh pr-open`. This repo's `.stark-gh.json` already provides the audited merge waivers `allowSecretCommit` and `allowSecretToLlm`; `idun gh pr-merge` reads them without extra flags.

## Adding a formula (or cask)

**CLI → formula.** Copy an existing formula, then: keep its native auth headers and token validation, point `homepage`/`url` at the new private repo, and update `install` for the shipped binaries (`bin.install "alfred", "alfredd"` names them explicitly; `bin.install Dir["lumiere", "lumiere-*"]` globs — a bare dispatcher name needs its own literal, since `lumiere-*` does not match it). The bumper never creates an entry, so this hand PR pins `version`/asset-id/`sha256` to the first release: once the file exists, `scripts/bump.sh <entry> <tag> --no-pr` fills them in. Every later release bumps them. Update `README.md` in the same PR, caller table included.

**Node-ESM CLI → formula** (`Formula/brain.rb` is the model). Not a single compiled binary: the release zip is a **`pnpm deploy` tree** (`dist/` + a vendored `node_modules` with the workspace deps and the signed native modules) plus any runtime data the CLI reads from disk. `install` does `libexec.install Dir["*"]` (the whole tree, layout intact — relative pnpm symlinks survive `ditto`) and writes a `bin` wrapper that runs the entry under a runtime dep (`depends_on "node"`; `exec "#{formula_opt_bin("node")}/node" "#{libexec}/dist/bin.js" "$@"`). brain also `export`s `ATLAS_ROOT="#{libexec}"` so it finds its bundled command registry without walk-up. `test do` asserts `version.to_s` against the tool's own `version` output. Same three release-specific lines left to the bump tooling.

**Bun source-tree CLI → formula** (`Formula/sleipnir.rb` and `Formula/lucius.rb` are the models). No build step at all: the release zip is the runnable TypeScript tree plus a vendored prod `node_modules`, at the zip's top level. `install` does `libexec.install Dir["*"]` (so keep the zip free of top-level dotfiles — `Dir["*"]` skips them) and writes a `bin` wrapper over `depends_on "bun"`: `exec "#{formula_opt_bin("bun")}/bun" "#{libexec}/bin/<entry>.ts" "$@"` (lucius). sleipnir's tree is a workspace since 0.11.0, so it writes one wrapper per command over `#{libexec}/apps/<app>/bin/<entry>.mjs` (`slp`/`sleipnir` → `apps/sleipnir`, `huginn` → `apps/huginn`, `sleipnir-mcp` → `apps/mcp`, the MCP server an agent client starts from its own working directory); its bumper never rewrites them, so a launcher move is a hand edit in that release's tap PR. A bare `sleipnir` resolves to homebrew/cask's browser, so name the formula `21StarkCom/tap/sleipnir` in every `brew` command. Add `--no-env-file --config=/dev/null` when the CLI must not inherit the caller's cwd `.env` or `bunfig.toml` preloads (lucius and sleipnir do; keep the matching `test do` assertion). Homebrew cannot version-constrain a formula dependency, so a Bun floor enforced at runtime (lucius: `>=1.4.2`) is invisible to `brew install` — a Mac with a stale homebrew/core pours an old bottle, and only `brew test` catches it. Same three release-specific lines left to the bump tooling.

**GUI `.app` → cask** (`Casks/mimir.rb` is the model). Keep a uniquely named initialization-only adapter like `MimirPrivateReleaseStrategy` to set native `@meta[:headers]` without exposing credentials in cask JSON; then `app "X.app"` places the bundle in `/Applications`, `binary "#{appdir}/X.app/Contents/Resources/bin/<cli>"` symlinks a nested CLI onto PATH (a symlink, never a copy — the CLI resolves its own path to find the bundle executable it pins), `depends_on macos:` pins the build's deployment target, and `uninstall quit:` closes the running app, and any menu bar helper it opens (a login item with its own bundle id), on upgrade; never a `KeepAlive` launchd agent, which launchd relaunches at once. Every launchd job the app registers, login item included, goes in `zap launchctl:`, never `uninstall launchctl:`: Homebrew runs every `uninstall` directive but `signal` on `brew upgrade` too. Ideally the release zip contains the notarized + **stapled** `.app` at its root (mimir does). The atlas cask is the exception: its `Atlas.app` is notarized but **not stapled**. Homebrew installs a cask's app quarantined on every install or upgrade, so Atlas's first launch after each checks its notarization online. Same three release-specific lines (`version`, asset id, `sha256`) — left to the bumper, `scripts/bump.sh`.

## Automated verification

`.github/workflows/bump.yml` runs `scripts/test-bump.sh` on ubuntu, and again in Docker Hub's `bash:3.2` image (3.2 is the oldest bash a signing Mac runs bump.sh under, as `/bin/bash`), for every PR, and `bump.sh --merge` waits for it along with the other two. Its test fails if the bumper's `GATE_WORKFLOWS` differs from the workflows here that trigger on `pull_request`, or if any of them filters that trigger: keep every such trigger unfiltered, and add a new one to `GATE_WORKFLOWS` in the same PR. `brew style … scripts` lints `scripts/*.sh` too, with every optional shellcheck check and Homebrew's `shfmt` layout (`brew style --fix scripts/bump.sh` applies it). Its layout pass misreads a line inside a string or heredoc that starts with `if`, so keep embedded jq, Ruby and stub code free of those.

`.github/workflows/formulae.yml` runs on ubuntu arm64 (`ubuntu-24.04-arm`: on x86, `brew fetch --cask` skips an arm64-only cask and exits 0), under Homebrew on Linux, with no macOS runner. It styles all entries, checks missing/blank token errors, audits and fetches every formula, and fetches every cask with the token (each fetch checks the download against its pinned `sha256`) and runs `brew audit --cask --strict` on it. Every entry is macOS-only, so Linux Homebrew installs none of them: CI runs no `brew install` or `brew test`, and the Commands' `brew reinstall` and `brew test` on a Mac are that check. The cask audit skips `sha256_no_check_if_unversioned` for every cask, since an asset-id URL reads as unversioned, and `token_conflicts` for atlas alone, which shares its token with a homebrew/core formula. It catches a gone or unreadable asset and a hand-edited asset id or `sha256` that no longer match; an id and checksum that agree but belong to another release pass. It uses the repository Actions secret `HOMEBREW_RELEASE_READ_TOKEN`, which must have contents-read access to the release repositories. Mimir remains the source of the credential; GitHub stores its encrypted CI copy. It fails if access is unavailable. The workflow also checks hermod preflight metadata and a seeded partial download against the pinned checksum. `scripts/verify-download.rb` must run with a dedicated `HOMEBREW_CACHE`, because it replaces its cached hermod archive with a partial to verify resume, and with the tap trusted (`brew trust --tap 21StarkCom/tap`, which the workflow runs where it registers the checkout), because `brew ruby` names no formula. `scripts/verify-auth.rb` uses only synthetic/missing credentials, with `HOME` pointed at an empty directory so a signed-in gh cannot supply a token. The workflow's gh-login step unsets the env token, signs gh in instead and asserts that Homebrew's lookup now resolves to the gh login, then fetches stark-statusline and the mimir cask: the gh fallback, end to end. The sandboxed workers' skip needs a Mac's `brew reinstall` and `brew test` with a gh-only login: Linux Homebrew installs none of the entries, so its build and test workers never load them.
